# MiniTask DevOps

A small FastAPI task API packaged with Docker and checked by GitHub Actions. It is intended as a starter project for practicing a Python test-and-build CI pipeline and running an API in a container.

## What is included

- **FastAPI API** with health and task endpoints.
- **Docker image** built from `python:3.12-slim` by the Dockerfile.
- **Docker Compose** service for building and running the API locally.
- **GitHub Actions CI** that installs dependencies, checks imports, runs pytest, and builds a Docker image.

## Requirements

- Python 3.12 for running the app and tests locally.
- Docker Engine/Desktop with the Docker CLI.
- Docker Compose v2 (`docker compose` command).
- A GitHub repository with Actions enabled to run the CI workflow.

## Run locally with Python

Create and activate a virtual environment, then install the development dependencies:

```bash
python -m venv .venv
```

On macOS/Linux:

```bash
source .venv/bin/activate
```

On Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Install dependencies and start the development server:

```bash
python -m pip install -r requirements-dev.txt
python -m uvicorn app.main:app --reload
```

The API listens at <http://localhost:8000>. Interactive API documentation is at <http://localhost:8000/docs>.

## Run with Docker

Build the image from the repository root:

```bash
docker build -t minitask:local .
```

Start a container and publish its port 8000 on your computer:

```bash
docker run --rm -p 8000:8000 --name minitask-api minitask:local
```

Visit <http://localhost:8000/health> or <http://localhost:8000/docs>. Stop the container with `Ctrl+C`. The `--rm` option removes the stopped container; omit it if you want to inspect the container afterwards.

### Run with Docker Compose

Compose builds the image from the local Dockerfile, maps host port 8000 to container port 8000, and restarts the service unless it is explicitly stopped:

```bash
docker compose up --build
```

Run it in the background with `docker compose up --build -d`. View logs with `docker compose logs -f api`, and stop the service with `docker compose down`.

## API endpoints

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Returns the API health status. |
| `GET` | `/tasks` | Returns the current task list. |
| `POST` | `/tasks` | Creates a task from a JSON title. Titles must be 3 to 80 characters. |
| `GET` | `/docs` | Interactive Swagger UI generated by FastAPI. |

Example request:

```bash
curl -X POST http://localhost:8000/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Learn Docker"}'
```

The API returns the new task with an ID and `done: false`. Task data is stored in memory, so it is cleared when the application process/container restarts; this project does not include a database.

## Tests

Install the development dependencies as shown above, then run:

```bash
python -m pytest -v
```

> **Current CI note:** `tests/test_api.py` expects `GET /health` to return `{"status":"success"}`, while `app/main.py` currently returns `{"status":"ok"}`. That test will fail until the expected value or endpoint response is made consistent. The workflow runs pytest before its Docker build, so this mismatch also prevents that workflow run from reaching the image-build step.

## GitHub Actions CI

The workflow is defined in [`.github/workflows/ci.yml`](.github/workflows/ci.yml). It runs on:

- Pushes to `main`.
- Pull requests targeting `main`.
- Manual dispatch from the GitHub Actions tab.

The `test-and-build` job runs on an Ubuntu runner and:

1. Checks out the repository.
2. Sets up Python 3.12.
3. Installs `requirements-dev.txt`.
4. Checks the project layout and imports the `app` package.
5. Runs pytest.
6. Builds a local Docker image tagged `minitask:ci`.

The Docker build is a CI verification step. The current workflow does **not** log in to a container registry, push an image, create a release, or deploy a container. The Compose and `docker run` instructions above build/run the image locally. To distribute an image, a registry publishing step and repository credentials would need to be configured separately.

## Project layout

```text
.
|-- app/
|   `-- main.py             # FastAPI application and in-memory task endpoints
|-- tests/
|   `-- test_api.py         # API tests
|-- .github/workflows/
|   `-- ci.yml              # GitHub Actions test and Docker build workflow
|-- Dockerfile              # Builds the Python API image
|-- compose.yaml            # Local Compose service configuration
|-- requirements.txt        # Runtime dependencies
`-- requirements-dev.txt    # Test dependencies plus runtime dependencies
```
